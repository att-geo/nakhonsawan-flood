## 4. โมเดล (`pipeline/model.py`)

ต่อ hex *i* ต่อชั่วโมง *t*

1. **ฝน**: IDW 4 จุด grid → P(t). ปรับแก้ 24 ชม. ล่าสุดด้วย ratio = (G+2)/(M+2) ที่สถานี (จำกัด 0.2–5), interpolate log-ratio ด้วย IDW, น้ำหนักเต็มภายใน 10 กม. ลดถึง 0 ที่ 40 กม.
2. **น้ำท่า SCS-CN** แบบเหตุการณ์ (เริ่มเหตุการณ์ใหม่เมื่อฝนหยุด ≥ 12 ชม.)
   S = 25400/CN − 254, Ia = 0.2S, Q = (P−Ia)²/(P−Ia+S); CN ปรับ AMC I/III จากฝน 5 วันก่อนเหตุการณ์ (35/53 มม.)
3. **กักเก็บ** W(t) (มม.) ; น้ำปกติในคันนา N = 100·f_นา + 10 ; D_cap = N + 0.3·min(sink_mm, 60)
4. **ระบาย** Out = max(W − D_cap, 0)·(1 − e^(−1/T)) + 0.5·max(W − D_cap − 800, 0), T = clip(8/√slope%, 2, 96) ชม. × (1 − 0.3·f_เมือง)
5. **ร่องน้ำ** น้ำจากต้นน้ำผ่านร่องได้ Qc = 7.2·A^0.75·clip(√slope%, 0.5, 4) มม./ชม. (≈ bankfull 2·A^0.75 ม³/วิ, A = พื้นที่รับน้ำ กม²) ส่วนเกินล้นเข้าพื้นที่
6. **backwater** ถ้าสถานีใกล้เคียง (≤15 กม.) ระดับน้ำ > ตลิ่ง − 1 ม. และ HAND_major < 6 ม. → T×3, Qc/3
7. **สูญเสีย** 0.15–0.3 มม./ชม. เมื่อฝน < 2 มม./ชม. (ระเหย + ซึม)
8. **ความลึก** d = max(W − N, 0) / f_spread ; f_spread = clip(0.7·f_low + 0.15, 0.2, 0.85) ; hex ที่เป็นแหล่งน้ำถาวร (>50%) ไม่นับ
9. **น้ำล้นตลิ่ง** เมื่อ WL > ตลิ่ง: d_r = clip((WL − z_ref) − HAND_major_P10, 0, WL − ตลิ่ง)
10. d = max(d_ฝน, d_ล้นตลิ่ง) → ชั้น: <10 ไม่ท่วม, 10–25 เฝ้าระวัง, 25–50 ท่วมขังเล็กน้อย, 50–100 ปานกลาง, >100 ซม. ท่วมสูง
11. **ระยะเวลา**: ชั่วโมงต่อเนื่องที่ d ≥ 10 ซม. ถึงปัจจุบัน (จากการจำลองฝนอย่างเดียว); เวลาที่เหลือ = ชั่วโมงแรกในอนาคตที่ d < 10 ซม. จากการจำลองรวมฝนพยากรณ์ + น้ำล้นตลิ่ง (ถ้าเกิน 72 ชม. ใช้อัตราการลด 12 ชม. สุดท้าย), เพดาน 14 วัน ;
    hex ที่ท่วมจากน้ำล้นตลิ่งอย่างเดียว: ท่วมมาแล้ว = ชม.นับจากสถานีหลักของลำน้ำที่ใกล้ที่สุด (≤ 10 กม.) ขึ้นเหนือตลิ่ง (ประวัติรายชั่วโมง 30 วัน) ;
    สรุปรายอำเภอ (`districts.json`): `dur_km2`, `h_med`/`h_max` (ท่วมมาแล้ว), `r_med`/`r_max` (คาดลดใน) เป็นค่ามัธยฐานถ่วงพื้นที่ท่วมจริง และ `r_km2` = พื้นที่แยกชั้น < 1 วัน / 1–3 / 3–7 / 7–14 / > 14 วัน ; ทั้งจังหวัดอยู่ใน `meta.summary.duration`

จำลองต่อเนื่องย้อนหลัง 30 วันทุกครั้ง (cold start แห้ง) จึงไม่ต้องเก็บ state ระหว่างรอบ

### ค่าเริ่มต้นและการทดสอบความไว (28 ก.ย. 2569)
พารามิเตอร์ข้างต้นตั้งจากหลักอุทกวิทยาและทดสอบกับฝนจริง (ฝนเฉลี่ย 7 วัน ≈ 134 มม.): ได้พื้นที่เฝ้าระวัง ~400 กม² ;
ฝน ×1.5 → ~1,300 กม², ×2 → ~2,300 กม² (โมเดลตอบสนองแบบไม่เชิงเส้นตามที่คาด) — **ยังไม่ได้สอบเทียบกับพื้นที่ท่วมจริง** ดูข้อ 6.1

### Near-realtime — `pipeline/upstream.py`
1. ฝนราย zone จากจุด grid 0.2° (Open-Meteo) ปรับแก้ 24 ชม. ด้วยสถานีโทรมาตร ThaiWater ในเขต 5 จังหวัด
2. SCS-CN ต่อเนื่อง → q (มม./ชม.) → Q = q·A/3.6 (ลบ.ม./วิ) → หน่วง lag + linear reservoir K = max(6, 0.5·lag) ชม. (FFT convolution) → hydrograph ที่จุดเข้า
3. **แม่น้ำสายหลัก** — ยึดค่าตรวจวัดจริง (RID) แล้วบวกการเปลี่ยนแปลงจากฝนต้นน้ำ
   `Q_fc(t) = Q_rec(t) + max(Q_model(t) − Q_model(now), 0)` ; ปิง = P.17, น่าน-ยม = N.67, แม่วงก์ = Ct.5A (`pipeline/gauges.py`)
   - `Q_rec` = ค่าตรวจวัดตอนนี้ → ถ้าน้ำกำลังขึ้น (แนวโน้ม 6 ชม.) ขึ้นต่อแบบหน่วง `Q0 + r·τ(1 − e^(−t/τ))`, τ = 12 ชม. แล้วลด `Qb + (Qpk − Qb)·e^(−(t−τ)/k)`
   - k (ชม.) = −1 / median(Δln(Q − Qb)) ของชั่วโมงที่น้ำลดต่อเนื่อง ≥ 6 ชม. ในประวัติ 30 วัน (จำกัด 12–360 ชม.; ไม่พอใช้ค่าเริ่มต้นราย reach) ; Qb = P5 ของ Q × 0.9
   - ส่วนเพิ่มจากแบบจำลองนับเฉพาะที่เป็นบวก (ฝนใหม่/คลื่นน้ำจากต้นน้ำ) ; เจ้าพระยา C.2 = Q_obs + ΔQ_ปิง + ΔQ_น่าน หน่วง 12 ชม. (ใช้ค่าตรวจวัดจริงย้อนหลัง + ค่าพยากรณ์)
   - สถานีที่ไม่รายงาน Q (เช่น Ct.5A): rating curve `Q = a(WL − z0)^b` ฟิตจากคู่ (WL, Q) ในอดีต (≥ 24 คู่), เหนือระดับสูงสุดที่เคยวัดใช้เลขชี้กำลัง ≤ 5/3 ; ไม่มี rating → Manning จาก qmax
   - ผลใน `upstream.json` ราย river: `recession` (k_h, q_base, trend_qph), `rating`, `overbank_since`, `h_below_bank` (ชม.ที่คาดว่า Q ต่ำกว่าความจุ)
4. **ที่ราบลุ่มน้ำล้นตลิ่ง (level-pool ตาม HAND)** — S(t+1) = S + max(Q − Q_cap, 0)·3600 − 0.5·max(Q_cap − Q, 0)·3600 − ระเหย 5 มม./วัน ;
   Q_cap = qmax ของสถานี RID ; ค่าเริ่มต้น S₀ = ปริมาตรใต้ระดับ (WL − z_ref) เมื่อสถานีล้นตลิ่ง ;
   ระดับ h(t) หาจาก ΣV_i(h) = S บน hex ของช่วงลำน้ำ (hex ใกล้สถานีในช่วงนั้น ≤ 15 กม. และ HAND_major P10 < 10 ม.) ;
   V_i(h) จาก CDF ของ HAND (P5, P10, P25, P50, P75) ; ความลึกเฉลี่ยในส่วนที่ท่วม = V_i/(A·F_i)
5. **ลำน้ำสาขา** (จุดน้ำเข้าที่ไม่ใช่แม่น้ำสายหลัก) → ฉีด Q·3.6 มม./ชม. เข้า hex cascade ของโมเดลน้ำท่วมขังที่ entry hex
   (ความจุร่องน้ำ Qc ของ hex ท้ายน้ำใช้ facc ที่รวมพื้นที่ต้นน้ำแล้ว)
6. ผลลัพธ์ `upstream.json`: hydrograph + พยากรณ์ของแต่ละแม่น้ำ, ปริมาตรน้ำเข้า นว. รายจังหวัด (7 วันที่ผ่านมา / 72 ชม. ข้างหน้า), พื้นที่ที่ราบลุ่มล้นตลิ่ง, สถานีต้นน้ำ ;
   `gauges_hist.json` ประวัติรายชั่วโมง 30 วัน `[t, Q, WL]` — ครั้งแรก/ข้อมูลขาดช่วง > 90 นาที ดึงย้อนหลังจาก ThaiWater `waterlevel_graph` (station id), รอบปกติเพิ่มค่าล่าสุด (เก็บต่อเนื่องผ่าน GitHub Pages)

### ข้อจำกัดเพิ่มเติม
- ไม่ได้พยากรณ์การระบายเขื่อนภูมิพล/สิริกิติ์/นเรศวร และน้ำจากสุโขทัย/อุตรดิตถ์ (อยู่ในค่า Q_obs ปัจจุบัน และลดตาม recession ของสถานี)
- recession แบบ exponential เดียวต่อสถานี ไม่แยกน้ำลดช่วงต้น (เร็ว) กับน้ำฐาน (ช้า) ; ช่วงขึ้นต่อ τ = 12 ชม. เป็นค่าสมมติ
- hex บนพื้นลาด (เช่น ลาดยาวตะวันตก) ที่ WSE สูงกว่าเพื่อนบ้านมาก ยังระบายช้าเกินจริง เพราะ weir_c สอบเทียบจากโดเมน 2D ที่ราบ → อาจได้ "> 14 วัน" ; ควรสอบเทียบเพิ่มด้วยโดเมน 2D ที่ลาดชันหรือ GISTDA
- ความเร็วน้ำเฉลี่ยเดียวทั้งภูมิภาค (0.7 ม./วิ) ไม่ได้แยกการหน่วงของบึงสีไฟ/ทุ่งบางระกำ (ใช้ K ช่วย)
- เพชรบูรณ์ส่วนใหญ่ไหลลงแม่น้ำป่าสัก จึงนับเฉพาะส่วนที่ DEM บอกว่าไหลเข้า นว. (ผ่านน้ำเข็ก/วังโป่ง → น่าน)

### แบบจำลอง v3 (`model.simulate_v3`) — ทุกชั่วโมง + substep 15 นาที
1. น้ำท่า SCS-CN → W (มม.) ; น้ำในคันนา N = 100·f_นา + 10 ; D_cap = N + 0.3·sink·dcap_mult
2. **ระบายตามทิศการไหลหลายทิศ**: max(W − D_cap, 0)·(1 − e^(−1/T)), T = clip(8/√S%, 2, 96)·t_mult/(1 + กม.คลอง) กระจายตามสัดส่วนไปยัง hex ปลายทาง (ถึงในชั่วโมงถัดไป)
3. **ท่อระบายน้ำเมือง**: 20·f_เมือง มม./ชม. (ลด 1/3 เมื่อน้ำเท้อ) ; **สถานีสูบ**: ≤ ความจุ·3.6 มม./ชม. ส่งไป hex แม่น้ำ
4. **ประตูระบายน้ำ**: เมื่อระดับน้ำสถานีใกล้เคียงอยู่ต่ำกว่าตลิ่งไม่ถึง 1 ม. hex ที่มีประตู → ปิด (ไม่ระบายตามแรงโน้มถ่วง เหลือแค่สูบ)
5. **Fill-spill / แผ่ด้านข้าง / ไหลย้อน** (4 substep): ระดับผิวน้ำ η จาก hypsometry ของน้ำอิสระ (W − N); ทุก edge ที่ η_สูง > sill:
   Q = 1.7·weir_c·w_eff·(η_สูง − max(η_ต่ำ, sill))^1.5 ; w_eff = 0.1·ความยาวขอบ ; จำกัดไม่ให้เกินครึ่งหนึ่งของผลต่างที่ทำให้ระดับเท่ากัน
6. ความลึก = ปริมาตรน้ำอิสระ / สัดส่วนพื้นที่ใต้ระดับ η (ความลึกเฉลี่ยในส่วนที่ท่วม) ; สัดส่วนพื้นที่ท่วม < 5% ถือเป็นน้ำในร่องน้ำ
7. **น้ำล้นตลิ่ง**: (Q_fc − Q_cap)·3600 ม³/ชม. (+ ปริมาตรเริ่มต้นจากระดับน้ำจริงเมื่อล้นตลิ่ง) ฉีดเข้า hex ลำน้ำหลักของ reach (ถ่วง f_low) แล้วให้ fill-spill กระจาย — คันกั้นน้ำ/ถนนกั้นได้ตามจริง ;
   รันสองรอบ (มี/ไม่มีน้ำล้นตลิ่ง) เพื่อแยกสาเหตุ (ฝน vs แม่น้ำ)
8. พื้นที่รายงานทั้งหมดถ่วงด้วยสัดส่วนพื้นที่ท่วมใน hex (ไม่ใช่นับทั้ง hex)

## 4e. การสอบเทียบ (`pipeline/calibrate.py` → `data/static/calibration.json`)
grid search t_mult ∈ {0.5, 1, 2}, weir_c ∈ {0.3, 1, 3}, dcap_mult ∈ {0.7, 1, 1.3} (27 ชุด) เทียบกับผล 2D:
คะแนน = RMSE สัมพัทธ์ของพื้นที่ท่วม ≥ 10 ซม. รายชั่วโมงในโดเมน + 0.5 × MAE ของสัดส่วนท่วมราย hex (สูงสุด 72 ชม.) ;
รันอัตโนมัติสัปดาห์ละครั้ง (อาทิตย์ 07:00 น.) หรือสั่งเองจาก Actions / ArcGIS Pro tool 2c

### เป้าหมายที่ 2: พื้นที่น้ำท่วมจากดาวเทียม GISTDA (`pipeline/gistda_obs.py`)
เมื่อตั้ง `GISTDA_API_KEY` แล้ว `run_update.py` จะ
1. ดึง `flood/3days` (แบ่งหน้า limit/offset) เขียน `gistda_flood.geojson` สำหรับแสดงบนแผนที่ (เหมือนเดิม)
2. **แปลง polygon เป็นสัดส่วนท่วมราย hex** (สุ่มกริด 200 ม. + even-odd scanline รองรับรู/MultiPolygon → hex ที่ใกล้ที่สุด) แล้วเก็บเป็นระเบียนรายวันใน `data/live/gistda_obs.json` ; หน้าต่าง 3 วันของ API เลื่อนหายไปเรื่อย ๆ จึงต้องสะสมเอง — ระเบียนละ ~ไม่กี่ร้อย hex, เก็บได้ 240 ระเบียน ; วันที่อ่านจาก property ของฟีเจอร์ (ชื่อที่มี date/time, ISO / dd/mm/yyyy / epoch / ปี พ.ศ.) ถ้าไม่มีจะผูกกับเวลาที่ดึงและถือเป็นภาพรวม 3 วัน
3. workflow กู้ไฟล์นี้จาก GitHub Pages ทุกรอบ และสำเนาสำรอง `data/static/gistda_obs.json` ถูก commit พร้อม `calibration.json` ทุกสัปดาห์

`calibrate.py` เพิ่มพจน์ GISTDA ในคะแนน: `คะแนน = คะแนน 2D + w × [(1 − CSI ราย hex) + 0.25 × |A_model − A_obs|/A_obs]` เฉลี่ยตามระเบียน โดย w = min(จำนวนระเบียน, 3)/3

**การจับคู่เวลาและข้อจำกัดของภาพดาวเทียม** (สำคัญต่อการตีความ)
| ประเด็น | วิธีจัดการ |
|---|---|
| ภาพเป็นรายวัน ไม่ทราบเวลาที่ดาวเทียมผ่าน | เทียบกับ **ค่าสูงสุดของโมเดลในหน้าต่าง** 48 ชม. ก่อนสิ้นวันของฟีเจอร์ (72 ชม. ถ้าไม่มีวันที่) ไม่เทียบ ณ ชั่วโมงเดียว |
| อาจไม่ครอบคลุมทั้งจังหวัด (เมฆ/แนวโคจร/ไม่มีภาพ) | ระเบียนที่พบน้ำท่วมรวม < 5 กม² ไม่ใช้ — "ไม่พบ" ไม่ถือเป็นหลักฐานว่าไม่ท่วม ; รายงาน POD และ FAR แยกกัน เพราะถ้าภาพครอบคลุมบางส่วน โมเดลจะถูกนับเป็น false alarm เกินจริง (FAR สูงแต่ POD ดี = สัญญาณว่าภาพไม่ครบ ไม่ใช่โมเดลผิด) |
| ภาพไม่ใช่ความลึก | เทียบเฉพาะ "ท่วม/ไม่ท่วม" ที่สัดส่วนพื้นที่ ≥ 10% ของ hex ไม่เทียบความลึก |
| แหล่งน้ำถาวร | hex ที่เป็นแหล่งน้ำ (`is_water`) ไม่นับทั้งสองฝั่ง |
| โมเดลจำลองย้อนหลังแค่ 30 วัน (cold start แห้ง) | ใช้เฉพาะระเบียนที่หน้าต่างเริ่มหลังจุดเริ่ม sim + 72 ชม. ; ภาพเก่ากว่า ~27 วันสอบเทียบไม่ได้จนกว่าจะขยายประวัติฝน (Open-Meteo archive) |
| ผัง hex เปลี่ยน | ระเบียนที่เก็บไว้ถูกล้างอัตโนมัติ (index hex ไม่ตรงกัน) |

ผลอยู่ใน `calibration.json` → `gistda_eval` (CSI/POD/FAR/ความคลาดเคลื่อนพื้นที่ของชุดที่ดีสุด เทียบค่าปัจจุบันและค่าตั้งต้น + ผลรายระเบียน) และ `at_grid_edge` (พารามิเตอร์ที่ค่าดีสุดอยู่ขอบ grid) ; `previous_score`/`baseline_score` คำนวณใหม่ภายใต้นิยามคะแนนเดียวกันทุกครั้ง จึงเทียบกับคะแนนเก่าที่เป็น 2D อย่างเดียวโดยตรงไม่ได้ (`scoring` = `2d` หรือ `2d+gistda`)

## 6. แนวทางยกระดับ

1. **สอบเทียบ** กับพื้นที่ท่วม GISTDA และ Sentinel-1 ที่แปลเอง — ทำแล้วแบบสะสมต่อจากนี้ (4e, 4f) ; ยังเหลือเหตุการณ์ใหญ่ปี 2554/2565/2567 ซึ่งต้องใช้ฝนย้อนหลังยาวกว่า 30 วัน
